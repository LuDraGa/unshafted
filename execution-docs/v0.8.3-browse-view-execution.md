# "What we've read" — browse view execution

**Status:** Code-complete, five gates green · 2026-09-22 · Branch `dev/v0.8.3`
**Design:** [`site-corpus-browse-design.md`](site-corpus-browse-design.md) — settled, read it first.
**Handoff it came from:** [`v0.8.3-handoff.md`](v0.8.3-handoff.md) §2.

The design doc argued what the corpus will and will not support. This one tracks building it, and
records the decisions taken at implementation time that the design doc left open.

---

## The four open questions, settled

The design doc ends with four questions "worth deciding before the component is written". All four
are now decided. Three went the way the doc leaned; §1 did not, for a reason the doc did not
consider.

### §1 — the row shows the count AND a `window` marker. Decided against the design doc.

The doc's position was count-only, with the counter-argument framed as scannability: 37 rows of
pure text are hard to read. That framing understates it, because of something the doc says two
paragraphs earlier and does not connect:

> **Typing dissolves the groups.** A query produces one flat result list.

The clock is carried *entirely* by the group heading. So the moment a reader types `ama`, they get
`amazon.com — 3 documents` and nothing at all indicating amazon is one of the 19 — even though the
view they were looking at two keystrokes earlier said exactly that. That is not a cosmetic loss. It
is the **search path silently dropping the view's only finding**, on the job the doc itself calls
primary.

So the marker earns its place on the search path regardless of what it does in the grouped view.
That leaves only: both modes, or search only? Both — one row component, one shape, no row that
changes form depending on whether a text field is empty. Inside `SOMETHING YOU CAN STILL DO` the
marker repeats the heading, and that repetition is the useful kind: the heading asserts a property
of the group, the marker shows it holding of each member. In `EVERYTHING ELSE` it is simply absent.

**Constraints the marker inherits from §3**, and which the implementation has to honour:

- The word is `window`, not `live`, `open`, `expiring`, or `deadline`. A `relative_to_signup`
  window needs the date the reader accepted and we do not have it (D14).
- Neutral tone, no severity colour. §4 keeps risk colour on the document cards.
- The §3 caveat travels with it via `title` / `aria-label`, because in search mode the group
  heading that defines the word is not on screen.

### §2 — browse does not persist. As the doc leaned.

D13's sticky availability is about not yanking a reader out of a surface *mid-session*. It is not an
argument for reopening the panel into a list of 37 sites instead of the site they are looking at.

### §3 — the empty result is honest text, and no button. As the doc leaned.

"We have not read notion.com." AD-6's "request an analysis" is where this leads, and it does not
exist, so nothing here pretends it does.

### §4 — the header entry point is deferred, not built.

Entry points 1 and 2 fill surfaces that are otherwise empty, so they cost nothing. The header one
competes with the domain name on every panel open, forever, and is much better judged against a
view that exists than in the abstract. Filed rather than decided.

## Decisions taken while building

### The domain detail keeps D10's order and drops both live claims

Opening a row renders header → `WorstRisk` → `OneThing` → the `DocumentCard` stack: the covered
view's own ordering, because it is the same information about the same documents and there is no
reason for it to be arranged differently when the reader arrived by search instead of by URL.

Two things from `CoveredView` must not come along, and both for the same reason — **you are not on
that site**:

- **`FreshnessStrip`.** Handed an empty freshness map, `overallFreshness` returns `pending` and the
  strip renders "Checking against the live page…". Nothing is checking anything. That is a false
  claim about our own behaviour, which is the cheapest kind to avoid and the easiest to ship by
  accident.
- **`DocumentReader`.** It reads the *active tab*. In browse the active tab is some other page, or
  `chrome://newtab`.

Cards render at `unconfirmed`, which is exactly true: "As we read it on 4 Sep 2026."

### The manifest is derived from the same grouping pass as the seed

`buildSeedRows` already groups analyses by domain and computes `hasTimeSensitiveAction`. The
manifest needs the same grouping plus a count. Rather than group twice, the grouping is lifted out
and both rows derive from it — which is `build-bundle.ts`'s own stated rule ("One command, one read,
no drift") applied to a third artifact. It also makes it structurally impossible for the seed and
the manifest to disagree about which domains exist.

### A fourth field, because the headline number is not derivable

The design's header sketch reads *"82 documents across 37 sites"*. Summing `documentCount` across
the rows gives **85**.

Three documents govern two domains each — one Disney terms across `disneyplus.com` and
`hotstar.com`, one Meta policy across `facebook.com` and `instagram.com`. A per-domain count has to
include them under both, or the domain is missing a document it is actually governed by. So the sum
is right for what it is and wrong for what the header says.

`documentTotal` is therefore a fourth field, carried rather than computed. It is not the speculative
kind #79 deleted six tokens for: it has exactly one consumer, and that consumer has no other correct
source. The field exists to make the wrong answer unavailable — without it, the next person to write
that sentence reaches for `reduce`, gets 85, and ships a number overstating the corpus by three on
the one surface whose job is to say how much we have read.

Both the schema and the loader carry the warning in a comment, because the trap survives the fix.

### A build-time cross-check, because the runtime cannot afford one

The loader zod-parses the manifest, so its *shape* is guarded at runtime. What the runtime cannot
check is whether it AGREES with the corpus — that needs both files, and the whole point of the
manifest is that browse does not parse 1 MB to render a list of names.

So `check-policy-corpus-plugin.ts` now cross-checks the domain sets and fails the build on a
disagreement in either direction. Drift here is not a crash: it is a row that opens into a detail
view with no documents, or a site we have read and will swear we have not. Both are silent, so they
are caught at build or not at all.

### Measured size

The design doc estimated 3,412 bytes raw / 646 gzipped. Measured on the real corpus at the shape
actually shipped — minified, no `generatedAt`, with `documentTotal` — it is **2,770 raw / 414
gzipped**. Smaller than estimated; the estimate was not load-bearing either way.

`generatedAt` is deliberately absent, unlike the corpus bundle: it would be the only changing byte
on a rebuild that found nothing new, and a diff that moves every time you run the script is a diff
nobody reads.

      name and format version in `corpus-bundle.ts`; derivation in `build-bundle.ts` off a grouping
      pass shared with the seed. Build-time cross-check in `check-policy-corpus-plugin.ts`.

      promise, `chrome.runtime.getURL`, no network. `useBrowseManifest` wraps it with a state that

      [#88](https://github.com/LuDraGa/unshafted/issues/88).

      `FreshnessStrip` and `DocumentReader` deliberately absent.
- [x] **6. Tests.** 8 assertions in `test/browse-view.test.tsx`, side panel 16 → 24.
      **Each was checked against the bug it guards** — dropping the marker fails 2, summing the rows
      for the headline fails 1, adding the freshness strip to the detail fails 1, and rendering an
      unavailable manifest as an empty list fails 1. Restoring passes all 8.
- [x] **7. Five gates.** `type-check`, `test`, `lint`, `format:check` run green here. `build` is the
      user's step and produces the `dist/` the manual QA loads.
- [ ] **8. Manual check on a loaded extension** — the list at ~400px and narrower, the marker not
      reading as a warning next to a risk pill, and the two entry points on a `chrome://` page and
      on an uncovered site.

## Rules this work is running under

Carried from the handoff §3 and the design doc §3, restated because they are what the review of this
code should check against:

- **Silence is not absence.** No absent-disclosure tally renders anywhere in browse.
- **Never claim a window is live.** The marker says a window is *named*, never that yours is open.
- **One property, one spelling.** `hasTimeSensitiveAction`, as in `policy-seed.json` and
  `corpus-bundle.ts`. #82.
- **A field with no consumer does not ship.** Three fields, because three render. #79.
- **The badge path makes no network call, ever.** Browse adds none.
