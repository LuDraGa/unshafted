# v0.8.1 — maintenance release

**Worked:** 2026-09-09 · **Base:** `release` at `257ff43` · **Branch:** `dev/v0.8.1`
**Last updated:** 2026-09-13
**Status:** cut and verified. **Round 1 submitted 2026-09-09 and rejected** on listing copy, not on
the build. The rectification published on its own as a listing-only update to 0.8.0; the 0.8.1
package has still never published, and its next submission is round 2. `main` was merged and tagged
`v0.8.1` ahead of publication, deliberately. See *What happened after the cut* below.

A version cut for content that was already finished. Nine commits had accumulated on `release` with
no version behind them, and under the branch model `main` cannot move until a version goes live on
the Chrome Web Store — so the queue was stuck by design, not by neglect. 0.8.1 exists to flush it.

## Why 0.8.1 rather than folding this into v0.9.0

v0.9 is a UX revamp with its own plan (`v0.9-ux-revamp-plan.md`, `v0.9-attention-redesign.md`).
Bundling a dependency sweep and a ReDoS fix into it would leave both unshipped for however long that
takes, and would put a large feature change and a boring maintenance change in front of review as
one thing. Shipping the boring half first is cheaper and it unblocks three separate stuck items at
once — see *What this unblocks* below.

0.8.1 and not 0.8.2: only `v0.8.0` is tagged, locally and on the remote. Nothing had used 0.8.1.

## The review surface did not move, and that was checked

0.8.0 was the hard submission — the broadest permission Chrome grants, on an item carrying two
rejections. 0.8.1 moves none of what made that hard, verified at the time by diffing `main` against
`release` — `main` then still being 0.8.0, which is what users have. It is not that any more, so
anyone re-running this check should diff the `v0.8.0` tag instead:

- `chrome-extension/manifest.ts` — **comment only.** The `permissions` array and `host_permissions`
  are byte-identical. What changed is the note above them: it used to read *"NOT YET SUBMITTED — the
  live listing is 0.7.1"*, which was false the moment 0.8.0 published, and now records that the
  permission is approved and live and is therefore a baseline to stay consistent with rather than an
  argument still to be made. Worth stating precisely, because "no diff at all" was the original
  wording here and it was wrong in exactly the direction this document warns about.
- `cws/` — **no diff at the time of the cut.** Privacy policy, listing copy and privacy form were
  exactly what review approved. That stopped being true a week later, for reasons below.
- The live gist already matches `cws/privacy-policy.md`, diffed against the real gist rather than
  assumed.
- The ZIP is 32 entries with the pdf.js worker byte-identical to 0.8.0's.

So review sees an approved permission story with a new build behind it.

## The bookkeeping this uncovered

Preparing the checklist turned up that **all three post-approval steps for 0.8.0 were skipped.** The
0.8.0 work order's own §6 called for them and nothing enforced it:

1. `cws/privacy-form-snapshot.md` still read *"Version live: 0.7.1"* and *"not yet submitted for
   review"*.
2. `cws/store-listing-snapshot.md` still read *"the published listing is still the 0.7.1 copy"*.
3. `cws/rejection-history.md` had no 0.8.0 entry at all — it stopped at v0.7.1's approval.

A fourth, in shipped source: `chrome-extension/manifest.ts` carried *"NOT YET SUBMITTED — the live
listing is 0.7.1, which has no host permissions"* directly above `host_permissions`.

All four asserted the same false thing — that 0.8.0 had not shipped — while `cws/README.md` calls
this directory the source of truth for a dashboard that is not diffable. Corrected here.

The approval **date** was a second-order version of the same mistake. It was reconstructed from the
publish merge `90e5f73` on the reasoning that `main` only moves after CWS publishes, and marked as
inferred in three files. That marking was honest but the date should not have been there at all: a
merge commit records what a person did in this repo, not what a reviewer did in a dashboard, and the
branch model it leans on is the same model 0.8.1 then broke on purpose. The inference has since been
removed rather than restated — what is certain, and now all that is claimed, is that 0.8.0 was
approved on the first round and was live by 2026-09-09, because round 1 was rejected against it.

Worth naming the mechanism, because it will recur: these files go stale **silently**. Nothing in CI
reads them, no test asserts against them, and only a person opening the dashboard would ever notice.
The new checklist's §5 is written to be harder to skip, but that is a habit, not a guard.

## What this unblocks

Three things resolve the moment `release` reaches `main`, all for the same reason — they resolve
from the default branch:

- **The ghost PR checks.** `pull_request_target` workflows resolve from `main`, so every PR still
  shows a failing `eslint` (linting `main`'s 49 pre-existing errors), 19 dead e2e jobs, and a
  `dependabot` job from a workflow deleted in #14. Confirmed this session: on all three PRs merged
  today the `pull_request` run passed while the `pull_request_target` run failed.
- **CodeQL alerts 4 and 8.** Both describe code `release` has already fixed. CodeQL scans `main`.
- **The unshipped product changes** themselves.

**Resolved, for the first two.** Waiting for publication would have left them broken for as long as
review took, so `main` was merged on 2026-09-11 without it — see item 2 of *What happened after the
cut*. The third is still waiting on the store.

## What happened after the cut

Three things, none of them in the plan, and the order matters because it is why the version numbers
and the listing copy no longer line up.

**1. Round 1 was rejected on listing copy.** Submitted 2026-09-09, cited **Yellow Argon** — excessive
keywords — quoting back the ten-brand-name run in the bundled-corpus paragraph of the description.
Nothing in the ZIP, the manifest, the permissions, the single purpose or the privacy policy was cited.
The uncomfortable part is that the same paragraph had been approved four weeks earlier as part of
0.8.0, unchanged: **approval is not precedent**, and this document's own confidence that the review
surface "did not move" was protection against a different risk than the one that landed. An appeal was
available and deliberately not taken. Full entry in `cws/rejection-history.md`.

**2. `main` moved before publication, on purpose.** `release` merged to `main` at `9d63cb1` and tagged
`v0.8.1` on 2026-09-11, while 0.8.0 was — and still is — the live version. That is a direct exception
to the rule in `CLAUDE.md` that `main` moves only when a version goes live, and the merge commit and
tag message both say so rather than eliding it. The reason is the third item under *What this unblocks*
above: the ghost `pull_request_target` checks and CodeQL alerts 4 and 8 all resolve from the default
branch, so nothing could clear them while `main` sat three weeks behind. It worked — `main` and
`release` now carry identical trees. It is recorded as a one-off in issue #66, and from 0.8.2 the flow
is followed without exception.

**3. The rectification shipped without the package.** The rewritten description and new graphic assets
went up as a **listing-only update against the live 0.8.0 item**, submitted 2026-09-11 and published
2026-09-13. Three of the five screenshots were replaced and both promo tiles were filled for the first
time. So the listing copy drafted *for* 0.8.1 is live *as* 0.8.0's, the citation is closed, and the
0.8.1 package resubmission now moves no review surface at all.

The knock-on for this repo is that `cws/` spent the interval asserting things that had stopped being
true — that the description was an unpasted draft, that the promo tiles were empty, that the screenshot
set was a plan. Reconciled on 2026-09-13, the same day the listing published, by a person reading the
files. The mechanism named above has not changed: nothing in CI reads them.
